# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

`pasejo` is an age-encrypted password manager for teams, written in Rust. It is a re-implementation of [passage](https://github.com/FiloSottile/passage) that supports multiple stores, multiple recipients/identities (age and SSH keys), TOTP/HOTP, and configurable sync hooks.

## Build & Development Commands

```sh
cargo build                  # compile
cargo test                   # run all tests (requires a display for clipboard tests)
cargo test --test trycmd_tests  # run CLI snapshot tests only
cargo test --test interactive_tests  # run interactive PTY-based tests (unix only)
cargo test -- --ignored      # run slow tests (e.g. RSA key generation)
cargo +nightly fmt           # format with rustfmt (rustfmt.toml uses nightly-only options)
cargo clippy -- -W clippy::pedantic -W clippy::nursery -W clippy::unwrap_used -W clippy::expect_used # lint
```

Releases are tagged in GitHub; release notes are auto-generated by GitHub's release UI from merged PR titles. There is no `CHANGELOG.md` file in the repository — put behavior-changing notes in PR descriptions instead.

## Testing

**trycmd snapshot tests** live in `tests/cmd/**/*.md` and `docs/commands/pasejo-cmd-*.md`. Each `.md` file is a fenced shell session — the test runner executes the commands and compares output. When output changes, update the `.md` file (or run with `TRYCMD=overwrite` to auto-update). The `PASEJO_CONFIG` env var is set to `config.toml` for all trycmd tests so they don't touch the real user config.

Each trycmd test has companion `.in/` and `.out/` directories that trycmd copies as the working directory before/after the test. Make sure the `.in` and `.out` folders remain in a pushed Git repository by creating empty files called `.keep` and these folders for each test. Only add these `.keep` files if there is no other file in those folders and remove the `.keep` files in case a file is added.

**Language-specific trycmd suites** live in `tests/cmd-{de,es,fr,it,ja,ko,zh}/**/*.md`. The corresponding `cli_tests_{lang}` functions in `tests/trycmd_tests.rs` set `LANG` and `LC_ALL` to the language code so the binary picks the right Fluent bundle and asserts the translated strings. Add a case to each language suite when adding a new user-facing message that should be exercised end-to-end.

**Interactive tests** (`tests/interactive_tests.rs`) use `rexpect` to drive PTY sessions for commands that prompt for input (e.g. `secret add`). These run serially (`#[serial]`) because they use `set_var("PASEJO_CONFIG", ...)`.

**Shared integration scaffolding** lives in `tests/common/mod.rs` (a `mod.rs`, so cargo doesn't treat it as a test target). It exposes `pasejo(config)` — an `AssertCommand` pre-wired with `PASEJO_CONFIG` + a pinned `en` locale — and a chainable `StoreScaffold::new().store(name).identity().recipient().secret(name, value)` builder over the fixed `TEST_PRIVATE_KEY`/`TEST_PUBLIC_KEY`. The binary-spawning crates (`browser_host_tests.rs`, `recipient_download_tests.rs`) pull it in with `mod common;`; `interactive_tests.rs` does not, because its rexpect/`set_var` shape doesn't fit. trycmd has no fixture-sharing primitive (every case copies its own `.in/`, and `identity add --file` validates existence), so `dev/new-trycmd-test.sh <path> [--no-identity]` stamps out the `.in`/`.out`/`.keep` + `some-identity` fixture for a new snapshot case. The merge engine's matrix is unit-tested directly in `cli/merger.rs`, so `tests/cmd/store/merge` keeps only `merge.md` (clean-merge wiring), `merge-conflict-all.md` (all three conflict messages), and `merge-rename-recipient.md` rather than a case per type.

**Unit tests that exercise i18n** must call `cli::i18n::init_for_tests()` at the top. Unit tests don't go through `main`, so `init` never runs and `fl!` calls otherwise return placeholders like `No localization for id: "…"`. The helper is idempotent (uses `Once`), so call it freely.

**Toolchain** comes from breto: `.breto.edn` lists the `@rust` and `@lint` groups, and `breto env` puts them on `PATH`. `rust-toolchain.toml` selects the stable channel; the nightly toolchain is only for rustfmt. A tool the project needs belongs in `.breto.edn`.

**Locale in local test runs** — the i18n loader follows gettext precedence (`LANGUAGE` > `LC_ALL` > `LC_MESSAGES` > `LANG`). The test harnesses set or remove `LANGUAGE` themselves, so a shell `LANGUAGE` does not leak into the snapshot or localized assertions.

**Always run `cargo +nightly fmt` over the whole project after any Rust source change**, before reporting the task complete. `rustfmt.toml` uses unstable options (comment wrapping, `StdExternalCrate` import grouping) that stable rustfmt ignores with a warning, so hand-written edits and stable-formatted code don't match.

## Architecture

### Module layout

- `models/` — core data types
  - `cli.rs` — all clap structs (`Cli`, `Commands`, and every `*Args`/`*Commands` enum)
  - `configuration.rs` — `Configuration` (user config, TOML via the `toml` crate + `atomic_write`) and `StoreRegistration`. Process-wide cache via `Configuration::cached() -> &'static Configuration`.
  - `password_store.rs` — `PasswordStore` (encrypted store payload: recipients, secrets, otp maps); implements `Zeroize`/`ZeroizeOnDrop`
- `commands/` — one file per top-level subcommand; each exposes a `dispatch` function called from `main`. Dispatch functions take `&Configuration`; mutating helpers clone or take `&mut Configuration` so read-only subcommands skip the clone.
  - `store_op.rs` — the funnel for "decrypt → mutate → encrypt + hooks". See [Store-op funnel](#store-op-funnel) below.
  - `browser.rs` — `browser query` / `browser host` dispatch. See [Browser query and host](#browser-query-and-host) below.
- `cli/` — shared CLI utilities:
  - `parser.rs` — clap value parsers and validators (store name, line number, file existence)
  - `completer.rs` — dynamic shell completers (case-insensitive store-name prefix matching)
  - `prompts.rs` — inquire wrappers for password / confirmation / editor prompts
  - `clipboard.rs` — copy + auto-clear with a Drop guard and desktop notifications
  - `atomic_write.rs` — sibling-tempfile + fsync + rename, with file mode `0600` on Unix
  - `i18n.rs` — Fluent-based user-facing string seam (see [Internationalization](#internationalization))
  - `sandbox.rs` — QR-decode sandbox (Linux-only Landlock + `fork()` child). See [QR sandbox](#qr-sandbox) below.
  - `constants.rs`, `environment_variables.rs`, `errors.rs` — small shared utilities
- `secrets/` — age encryption/decryption of the store file; stores are written mode `0600` on Unix
- `recipients/` — reading, formatting, and merging age/SSH public keys
- `identities/` — reading age/SSH private key files
- `hooks/` — executing configured pull/push shell commands; throttling via timestamps in the local data dir
- `one_time_passwords/` — TOTP/HOTP generation and parsing. HOTP counters are **post-increment** (use the stored value, then bump), matching RFC 4226 conventions.
- `downloader/` — fetching public keys from Codeberg/GitHub/GitLab by username. `ureq` has no default timeout, so the agent must be built with an explicit `timeout_global` (see `downloader/keys.rs`). The `CODEBERG_HOST`/`GITHUB_HOST`/`GITLAB_HOST` overrides may carry a scheme: a bare host keeps the secure `https://` default, while an explicit `http://host:port` reaches a self-hosted instance (or a test fixture) over plain HTTP. `classify_download_error` maps a failed `.call()` to a distinct localized message per cause — `404` → user-not-found (names the username), `429` → rate-limited, other non-2xx → server-error (with the status), `Timeout` → timed-out, everything else (DNS/TLS/connection) → the generic `error-downloading-public-key-failed` with the underlying error kept in the chain. The success path and every failure branch are exercised hermetically in `tests/recipient_download_tests.rs` against an in-process loopback HTTP server (with a German gate on the 404 message, since these network-path strings can't be driven by the trycmd language suites); the `recipient add --codeberg/--github/--gitlab` trycmd cases keep only their offline username-validation assertion so the default suite never touches the live internet.
- `exporters/` — Bitwarden JSON export
- `browser/` — domain matcher, JSON protocol types, and the native-messaging stdio loop backing the `browser query` and `browser host` subcommands. See [Browser query and host](#browser-query-and-host) below.

### Data flow

1. `main` parses `Cli`, loads `Configuration` (from `$PASEJO_CONFIG` env or OS config dir).
2. Command dispatch calls the relevant `commands/*.rs` module with `&Configuration`.
3. Most commands route through `commands::store_op::with_store` / `with_store_then`, which:
   1. Selects a `StoreRegistration` from the config (or bails with the localized "no store" error).
   2. Runs pull hooks (subject to throttling via `hooks/files.rs`).
   3. Acquires an exclusive advisory file lock on the store file (stdlib `File::lock`, stable since 1.89).
   4. Decrypts the store via `Configuration::decrypt_store`.
   5. Runs the caller's closure, which may mutate the `PasswordStore`.
   6. If the closure returned `StoreMutation::Modified`, re-encrypts and writes back via `secrets::encrypt`.
   7. Releases the lock.
   8. Runs the optional `then` callback (for actions like display / clipboard that should print between encrypt and push).
   9. Runs push hooks if modified.
4. The bootstrap path (`recipients::add` when the store file doesn't exist yet) bypasses `with_store_then` because there is no file to decrypt or race over; it constructs an empty `PasswordStore`, encrypts, and creates the file.

### Store-op funnel

Every command that touches a store goes through `commands::store_op::with_store` or `with_store_then`. The funnel guarantees: pull hooks run before decrypt; the decrypt → mutate → encrypt window is serialized by an OS file lock so concurrent `pasejo otp show foo` invocations cannot lose HOTP counter increments; push hooks run after the lock is released. Read-only operations still take the lock so they can't read a half-written store.

The closure signature is `FnOnce(&StoreRegistration, &mut PasswordStore) -> Result<(T, StoreMutation)>` — return `StoreMutation::Unchanged` for read-only flows so encrypt and push hooks are skipped.

Shared pieces so the funnel is not hand-rolled elsewhere: `store_op::open_store` performs the front half (select → pull hooks → file lock → decrypt) and returns an `OpenStore { registration, hooks, lock, store }`; `with_store_then` is built on it, and `otp::show` reuses it for its deliver-before-persist tail (the one flow whose tail genuinely differs). `store_op::require_store` is the single store selector that distinguishes "unknown store name" (`error-unknown-store`) from "no stores configured" (`error-no-store-in-configuration`) — every command that needs a store (`export`, `hooks::run`, `stores::{decrypt,merge,exec,remove}`, `recipients::add`, `otp::show`) routes through it rather than collapsing the two cases. `HookExecutor` is constructed via `HookExecutor::new(...)` (throttled) or `::forced(...)` (`hook run`, bypasses the throttle), not a struct literal — its fields are private. The browser host keeps its own `open_store_for_read` because it must classify each step's failure into a distinct `ErrorKind` that an `anyhow` chain would erase.

### QR sandbox

`pasejo otp add --qrcode <file>` feeds attacker-controlled bytes through the `image` and `rqrr` parsers — the largest untrusted-input parser stack in the codebase. To bound the blast radius of a memory-corruption bug in either crate, the decode runs through `cli::sandbox::decode_qrcode_to_otpauth_url`:

- On **Linux**, the function `pipe(2)`s, `fork(2)`s, and lets the child read the QR bytes into memory, install a Landlock ruleset that denies every `AccessFs` right reported by the running kernel (BestEffort against `ABI::V1`), then run `image::load_from_memory` + `rqrr` on the in-memory buffer. The decoded `otpauth://` URL — or a tagged error message — is written back to the parent over the pipe. The parent never restricts itself, so the surrounding decrypt → encrypt → hooks pipeline keeps working.
- On **non-Linux** targets (and on Linux kernels too old for Landlock), the decode falls through to an in-process call to `decode_qrcode_from_file`. The byte→URL contract is identical; the sandbox is purely additive defence in depth.

The fork-based architecture is mandatory because Landlock is permanent for the calling process once `restrict_self` returns. The parent has to remain unsandboxed to keep reading/writing the store, identity files, and hook timestamps.

The pure helper `decode_qrcode_bytes(bytes, qrcode_display) -> Result<String>` is exposed to make the parser stack unit-testable without forking or filesystem fixtures.

### Browser query and host

`pasejo browser query <DOMAIN>` searches the selected store for credentials matching `<DOMAIN>` and prints the results as JSON on stdout. `pasejo browser host` runs the same matcher as a long-lived native-messaging host: the browser spawns it per its native-messaging manifest, exchanges length-prefixed JSON over stdin/stdout, and closes the pipe when the user closes the browser. `pasejo browser install-manifest` writes that native-messaging manifest (and a small launcher wrapper) into the per-user paths each browser searches.

**Matcher** (`src/browser/matcher.rs`) — runs against a decrypted `PasswordStore` and returns `Vec<Match>`. Per secret, it scans the multiline fields named by `--uri-keys` (default: `uri url link site`) for URL values; an exact host match scores 1.0, a same-registrable-domain match scores 0.9. With no URL field, it falls back to a path-segment match on the secret name (split on `/` and `\`, segment-equal-or-`.`-suffixed against the registrable domain), scoring 0.5. The registrable-domain comparison uses the `psl` crate, which embeds a compile-time-generated public-suffix-list trie — required so that `example.co.uk` and `attacker.co.uk` are not treated as same-domain. The embedded list ages with the binary; a release built today knows today's public suffixes.

**Protocol** (`src/browser/protocol.rs`) — JSON wire format: `RequestEnvelope` wraps an optional `request_id: u64` around the action-tagged `Request` enum (`query` and `list_stores`); `ResponseEnvelope` wraps the same `request_id` (echoed verbatim, omitted from serialization when `None`) around `ResponsePayload`, an `untagged` enum of `QueryResponse` / `ListStoresResponse` / `ErrorResponse`. Active `ErrorKind` variants are `unknown_store`, `decode_error`, `identity_locked` (no identity unwraps the store — locked age identity, missing identity, wrong recipient, plugin failure), `hook_failed` (pull hook returned non-zero), `store_unreachable` (file missing, permission denied, lock contention, an age header or payload that does not parse, a plaintext that is not a store; `host.rs::decrypt_error_kind` draws the line), `no_store_configured`, `response_too_large` (the serialized reply would exceed the 1 MiB host→browser native-messaging limit; `serialize_capped` in `host.rs` downgrades the oversized reply to this fixed-shape error, preserving `request_id`, so the browser doesn't kill the whole connection and fail every in-flight request). `unknown_action` is defined but `#[allow(dead_code)]` — reserved for a future two-step parse that needs to distinguish "JSON parse error" from "action field is unknown"; today, both surface as `decode_error` with the serde message in `hint`. `ListStoresResponse` carries `protocol_version` (currently `1`) so the extension can refuse a mismatched binary; the extension checks exact equality and bumping this number is the single mechanism for signalling a breaking change. There is no `copy` action: fill is the only credential-extraction path the extension exposes; users who need the clipboard (paste into a non-browser app, copy the OTP code shown in the popup) reach for `pasejo secret show --clip` / `pasejo otp show --clip` directly, which gives them the CLI's full clipboard pipeline (auto-clear, notify, Ctrl-C interrupt).

The extension always sends `request_id` and always expects to see it echoed back; the optional handling on the host side is purely a defensive parse mode so a malformed payload can still produce a useful error reply when its top-level `request_id` was parseable. `decode_error_request_id` does that best-effort recovery from raw bytes when the full envelope deserialization fails.

**Host loop** (`src/browser/host.rs::run`) — checks `stdin().is_terminal()` at startup and bails with the localized `error-browser-host-requires-pipe` if a real TTY is attached. Constructs an `Arc<Configuration>` and an `Arc<HostContext>` (owns its `--uri-keys` / `--username-keys` rather than borrowing, so workers can capture by clone) plus an `Arc<Mutex<Stdout>>` for serialised writes. Spawns a fixed pool of `HOST_WORKER_THREADS` (16) detached worker threads, each running `worker_loop`, sharing an `Arc<Mutex<mpsc::Receiver<Vec<u8>>>>`. Main reads length-prefixed bytes (`read_message`, capped at `MAX_MESSAGE_LEN` = 1 MiB to match Chrome's documented native-messaging limit) and pushes the raw bytes through a `mpsc::sync_channel` of depth `HOST_WORKER_QUEUE_DEPTH` (32). When the queue is full the `send` blocks — that's the load-bearing back-pressure: a misbehaving caller can't outrun the host into memory exhaustion. Workers race to take the next slot, parse, dispatch, serialise the `ResponseEnvelope`, and write to stdout under the shared mutex. EOF on stdin exits the read loop; main drops the sender and returns. Idle workers exit when `recv()` returns `Err`; in-flight workers (e.g. blocked on a YubiKey touch) are killed by the OS when the process exits — read-only on the store file, lock released by the OS on fd close, pull hooks restartable, age plugins exit on stdin EOF, so this is safe. Pool size is fixed rather than CPU-derived because the workload is I/O-bound (decrypt, ssh-agent, age plugins, hook subprocesses) rather than CPU-bound; 16 covers realistic store counts with headroom.

Worker-per-request parallelism is what makes a YubiKey-blocked decrypt for store A not gate stores B–N: each request gets its own thread, holds its own file lock for its own store, talks to its own ssh-agent socket / age plugin, and only its own slot waits on the touch. Stdout serialisation is the only shared write surface; the mutex guarantees length prefix + payload land atomically without interleaving from another worker. Hook runs are the one exception to that parallelism: `hooks/executor.rs::directory_guard` serialises them per store directory within the process, so two stores in one git work tree never run `git pull` there at the same time.

**Decrypt-per-request, no in-memory unlock** — `handle_query` runs a hand-rolled equivalent of the `store_op::with_store` funnel (minus the encrypt + push tail a read-only query never needs): pull hooks fire (throttled), the file lock is acquired through `try_acquire_store_lock` (waiting at most `STORE_LOCK_WAIT`, 5 s, so a `secret edit` holding the lock for a whole editor session yields `store_unreachable` instead of pinning a worker), decrypt runs, the matcher runs, the lock is released. The funnel itself is not reused because routing every failure through `with_store` collapses them into a single anyhow chain — the host needs to classify each step's failure into a distinct `ErrorKind` (`hook_failed` / `store_unreachable` / `identity_locked`) so the extension can surface the right fix instead of always advising ssh-agent. `acquire_store_lock` returning `Ok(None)` (the bootstrap path — registered store, no file yet) is mapped to `store_unreachable` for the same reason: the browser host is never the right entry point for bootstrapping. Concurrent CLI edits during the host's lifetime stay safe via the file lock. The trade-off is no "unlock once for the session" UX: every query re-decrypts. SSH-agent is the documented unlock path because it handles the multi-decrypt cost without re-prompting; encrypted age identities would need a passphrase the host has no TTY to read, surfacing as `identity_locked` so the extension can show a useful message instead of the host hanging.

**Error hint redaction** — `error_response` formats the anyhow chain with `format!("{err:#}")` and then runs `redact_sensitive_paths` over the result before shipping it as `hint`. Every occurrence of the store's `Path::display()` form is replaced with the placeholder `<store>` and every configured identity path (global + per-store, deduped via `Configuration::all_identity_files`) is replaced with `<identity>`. Substitution is longest-first so a nested identity path inside the store's directory cannot fragment the outer match. The redaction is defence-in-depth, not a security boundary: paths that leak through a different formatter (`{:?}` debug, canonicalised forms from upstream crates) keep their original shape. The goal is to keep absolute paths off shared screens and out of support-channel screenshots, not to enforce a privacy invariant. The structured `store` field on the error response still carries the user-chosen store name — names are not filesystem leaks and the popup needs them for routing.

**Browser-spawned environment** — Native-messaging hosts inherit a stripped environment. `$HOME` is set but `$PASEJO_CONFIG`, `$PASEJO_DEFAULT_STORE`, and `$SSH_AUTH_SOCK` may not be. Pin them in the launcher wrapper that the manifest's `path` field points at — the native-messaging manifest itself accepts no `args` field, so any env-var pinning has to live in a shell wrapper.

**Install-manifest** (`src/browser/install_manifest.rs`) — `pasejo browser install-manifest --browser <NAME>...` writes the per-user JSON manifest each browser looks up before spawning the host. Supported browsers: `firefox`, `chrome`, `chromium`, `brave`, `edge`, `vivaldi`, `opera`. The module hard-codes the per-browser per-OS lookup directories (Linux: `~/.mozilla/native-messaging-hosts`, `~/.config/<browser>/NativeMessagingHosts`; macOS: `~/Library/Application Support/<vendor>/NativeMessagingHosts`); genuinely unsupported OSes return `error-browser-install-manifest-unsupported-os`. **Windows** locates hosts via the registry rather than a directory, so there the manifest is written under the data dir (`<data_dir>/native-messaging/<browser>/wtf.metio.pasejo.json`) and `register_native_host` (the `#[cfg(windows)]` `winreg` path) writes an `HKCU\Software\…\NativeMessagingHosts\<host_name>` value pointing at it; the wrapper is a `.cmd` batch file instead of a POSIX script. The platform-specific *policy* (`windows_registry_subkey`, `windows_manifest_path`, `windows_wrapper_content`, `posix_wrapper_content`) is pure and always compiled, so it is unit-tested on Linux; only the registry *write* is `#[cfg(windows)]`. CI compiles and tests the Windows path natively on the `windows-latest` runner (`x86_64-pc-windows-msvc`), and `dev/verify-windows-install-manifest.ps1` runs there to assert the registry value, manifest JSON, and `.cmd` wrapper for Chrome. Nobody has yet driven a real browser through the Windows host (see `docs/windows-verification-checklist.md`), and the Brave/Vivaldi/Opera registry subkeys and the Opera Linux/macOS directories are best-effort. Native-messaging manifests carry no `args` field — both Firefox and Chrome only allow specifying an executable `path` — so by default the command also installs a tiny wrapper at `<data_dir>/wtf.metio.pasejo` (Unix: a POSIX script, mode `0700`, `exec '<binary>' browser host`; Windows: a `.cmd`) and points the manifest's `path` at the wrapper. `--binary <PATH>` overrides this and references the supplied path verbatim with no wrapper installation, for callers who already maintain a launcher. `--print` emits the JSON to stdout and skips both wrapper creation and manifest writing. Firefox's `allowed_extensions` defaults to the bundled web-extension's gecko id (`pasejo@metio.wtf`); chromium-family browsers require `--extension-id` because their ids are derived from the unpacked extension's public key and cannot be predicted.

**Web extension** — the popup, content script, and native-messaging client live in a separate repo, [pasejo-web-extension](https://github.com/metio/pasejo-web-extension). Plain JS / HTML, no build step; manifests for Firefox MV3 and Chromium MV3 sit alongside the shared `src/`. Single-store queries open one `connectNative` per request (one host process per query). Multi-store queries open a long-lived popup↔background port via `runtime.connect({name:"query_multi_stream"})`; the popup sends one `{action:"start", requests:[…]}` and the background streams `{type:"result", index, response}` per store reply (plus a final `{type:"done"}`). The host's worker-thread parallelism is what keeps a slow store from blocking a fast one on the wire; the streaming port is what keeps a slow store from blocking a fast one on the *user-visible* render — the popup updates the `(answered/total stores answered)` progress counter and re-paints the results list as each store responds. Closing the popup disconnects the port, which signals the background to tear the native side down so the host process can exit even if a YubiKey prompt was in flight. Fill injects username + password and, when the match carries a TOTP code, **also fills a one-time-code field** if the page has one (`content/fill.js`: `findOtpInput` prefers `autocomplete="one-time-code"`, then a tight set of name hints — bare `code`/`token` excluded to avoid mis-filling a coupon/zip field; a standalone 2FA step with only the OTP field is a valid fill target). HOTP is excluded from the query response (emitting a code without bumping the counter breaks RFC 4226), so only TOTP autofills. The popup still shows the code as read-only text as a manual fallback. The extension UI is localized to the same eight languages as the CLI via WebExtensions `_locales/<lang>/messages.json` (English is `default_locale`); `protocol.js` exposes a `t()` wrapper over `i18n.getMessage`, popup status/error strings route through it, and the static HTML chrome is localized on load from `data-i18n*` attributes. A `tests/locales.test.js` drift-guard fails if any language strays from the English key set or drops a placeholder.

**Store resolution** (`host.rs::resolve_store`) — delegates to `Configuration::select_store`, the same chain every other command uses: explicit `store` in the request wins → `PASEJO_DEFAULT_STORE` env → config `default_store` → `stores.first()`. A request for a name that doesn't exist returns `unknown_store`; an empty configuration returns `no_store_configured`. There is no host-level store filtering or override flag — `browser host`'s CLI surface only carries the matcher's `--uri-keys` / `--username-keys`, matching the convention of every other pasejo command.

**Defaults sharing** — `--uri-keys` / `--username-keys` defaults live in `src/cli/constants.rs` as `DEFAULT_URI_KEYS` / `DEFAULT_USERNAME_KEYS` (const `&[&str]`) plus `default_uri_keys()` / `default_username_keys()` helpers consumed by clap's `default_values_t`. `BitwardenArgs`, `QueryArgs`, and `HostArgs` all reference the helpers so the three commands cannot drift on field-name conventions.

**Testing** — Matcher logic is unit-tested in `src/browser/matcher.rs`. `host.rs::tests` covers framing edge cases, `resolve_store` routing, `list_stores_response` default marking, `process_message` decode-error paths, and `request_id` round-trip / echo-on-error / non-numeric-id rejection. End-to-end URL-field coverage lives in `tests/interactive_tests.rs` (`browser_query_finds_url_field_match`, `browser_query_matches_subdomain_via_registrable_domain`) because injecting a multi-line secret with a `url:` field requires `secret add`'s non-TTY stdin path that trycmd cannot drive. End-to-end host coverage lives in `tests/browser_host_tests.rs` — currently 8 tests that spawn the binary with piped stdin/stdout. Two of them pin the v2 envelope contract (request_id round-trip on a query, absent request_id on a v1-style caller), and `host_processes_requests_concurrently_so_a_slow_store_does_not_gate_a_fast_one` sets up two stores where the slow one carries a `pull_commands = ["sleep 1"]` hook, pipelines both queries with request_ids 1 and 2, then asserts the fast store (id 2) answers first — proving the worker-thread parallelism actually swaps the response order. The TTY-detection branch is covered by `browser_host_refuses_to_start_with_tty_stdin` in `interactive_tests.rs` — rexpect attaches a PTY which trycmd cannot. The `error-browser-host-requires-pipe` key ships in all 7 language `.ftl` files but is only asserted in English; the translation gate is interactive-only because trycmd has no PTY.

### Configuration

Configuration is loaded from `$PASEJO_CONFIG` (env) or the OS-standard config dir (resolved by `directories::ProjectDirs::from("wtf", "metio", "pasejo")`). The config file is TOML. Two migration paths:

1. **Path migration** (`migrate_legacy_config_path`): one-shot relocation from the `confy`-era path (`ProjectDirs::from("rs", "pasejo", "pasejo")`) to the current path. Only relevant on macOS/Windows. Uses `move_file` which falls back to copy + remove on `CrossesDevices`.
2. **Schema migration** (`needs_migration` + `migrate_table`): only triggered when the on-disk TOML carries a marker that `migrate_table` would act on (missing top-level `pull_commands`/`push_commands`, a per-store `synchronizer` field, or per-store command arrays that haven't been initialized). Parse failures from typos or wrong types do **not** trigger a rewrite — they propagate as clean errors. `load_from_path` is the entry point.

Key env vars: `PASEJO_CONFIG`, `PASEJO_DEFAULT_STORE`, `PASEJO_DATA_DIR`, `PASEJO_DISABLE_HOOK_THROTTLING`, `CODEBERG_HOST`, `GITHUB_HOST`, `GITLAB_HOST`.

**Config-option single source.** A `config` option's knowledge lives in one place per concern: the `DEFAULT_*` constants at the top of `models/configuration.rs` are the only defaults — `config get` and every consumption site (`unwrap_or(DEFAULT_…)` in clipboard/hook/download paths) share them, so the printed default can't drift from the effective one; `ConfigurationOption::toml_key()` is the only TOML key string (matching the struct field) and `value_kind()` the only bool-vs-integer classification, both consumed by `config set`'s single arm. A `commands::config::tests` round-trip pins every `toml_key()` to a real serialized field of the right type, so a renamed field fails the build rather than silently writing an unreadable key.

### Internationalization

All user-facing strings (log lines, prompt labels, error messages, anyhow contexts) are routed through `cli/i18n.rs`. Fluent files live in `i18n/<lang>/pasejo.ftl`, embedded into the binary by `rust-embed`. English (`en`) is the fallback; other languages (`de`, `es`, `fr`, `it`, `ja`, `ko`, `zh`) ship full translations and fall back to English for any missing key.

`cli/i18n.rs` exposes one wrapper function per message id, generated by these macros:

| Macro | Shape it captures |
|---|---|
| `fl_log!(level, fn, key, args…)` | Logs `fl!(key, args)` through `info!` / `debug!` / `warn!` / `error!` |
| `fl_println!(fn, key, args…)` | Writes to stdout (list output, search hits) |
| `fl_notification!(fn, key)` | Bool→`String` for `notify-rust` clipboard notifications |
| `fl_log_path!(level, fn, key, arg)` | Single-`&Path` arg, rendered via `path_string` |
| `fl_println_path!(fn, key, arg)` | Same as above but `println!` |
| `fl_log_error!(level, fn, key)` | `&impl Display` error arg, converted via `.to_string()` |
| `fl_string!(fn, key, args…)` | Returns `String` for `anyhow` `context` / `bail!` / prompt labels |

A few wrappers are hand-written because they mix argument types (`list_store` takes `&str + &Path + bool`, `secret_copy_into_clipboard` takes `&str + &Duration`, `password_strength` takes `&str + f64`).

**To add a new user-facing string**:
1. Add the entry to `i18n/en/pasejo.ftl` with appropriate `{ $variable }` placeholders.
2. Add the `fl_*!` macro invocation to `cli/i18n.rs`.
3. Call the generated function from the production code site.
4. Translate the entry into the other 7 language files (`i18n/<lang>/pasejo.ftl`). Missing keys fall back to English at runtime, but you should backfill — the language-specific trycmd suites assert translated text, and `cli::i18n::tests::every_language_defines_exactly_the_english_key_set` fails the build if any language's key set diverges from English (and `every_english_message_has_a_wrapper_in_this_module` flags an `en` key with no `fl_*` wrapper).
5. If the new message fires from a code path that has unit tests, those tests must call `cli::i18n::init_for_tests()` before exercising the path.

**Technical strings that are NOT localized**: parse aliases like `true`/`false`/`yes`/`no`/`y`/`n`/`1`/`0` in `parse_bool`, env-var names, TOML field names, Fluent message ids themselves, and test fixtures.

## Code Conventions

- Rust edition 2024, MSRV 1.92, stable toolchain.
- `rustfmt.toml` enables unstable features, wraps comments, and groups imports as `StdExternalCrate`.
- Every file must start with SPDX headers:
  ```rust
  // SPDX-FileCopyrightText: The pasejo Authors
  // SPDX-License-Identifier: 0BSD
  ```
- Pedantic clippy passes (`-W clippy::pedantic -W clippy::nursery -W clippy::unwrap_used -W clippy::expect_used`). There is one known-ignored upstream future-incompat warning from `num-bigint-dig` / `wl-clipboard-rs`.
- Errors propagate via `anyhow::Result`. **Every user-visible** error/prompt string goes through `cli::i18n::*` (the `fl_string!` family) and ships in all 8 languages — never a hardcoded English literal. This includes `anyhow::bail!`/`.context(...)` text and the messages handed to `cli::errors::error_exit` (clap-style errors): use `.context(i18n::error_*())`, not `.context("hardcoded English")`. Add a language-suite gate (e.g. `tests/cmd-de/errors/de.md`) for new error messages so a regression is caught. The only accepted English-only exceptions are framework/bootstrap text we can't localize: clap's own built-in scaffolding (the `error:`/`Usage:` lines and its native `invalid value '…' for '<ARG>':` wrapper — only the body we supply is translated), the two `i18n::init` bootstrap errors (they fire before the loader exists), and the `browser/host.rs` native-messaging wire diagnostics (the web extension localizes those by `ErrorKind`).
- Sensitive values (`PasswordStore`, `OneTimePassword`, `Recipient`) implement `Zeroize`/`ZeroizeOnDrop`. Format-time strings derived from secret material (`format_code` in `commands/one_time_passwords.rs`) are wrapped in `Zeroizing<String>`.
- HOTP counter is RFC 4226 post-increment: emit at `counter`, then bump. `parse_otp_args` defaults `counter` to 0.
- Comments describe the **current** code: invariants, the why of non-obvious decisions, present-tense counterfactuals where helpful. Don't reference past versions, fix PRs, or review documents — readers see only the current code.
- The `debug-embed` feature on `rust-embed` is required for trycmd performance: without it every spawned binary reads i18n files from disk.

## Cargo dependencies of note

- `age` — encryption, with `armor`, `cli-common`, `plugin`, `ssh` features.
- `clap` derive + `clap_complete` (`unstable-dynamic`) for shell completion.
- `i18n-embed` + `i18n-embed-fl` + `rust-embed` (with `debug-embed`) — Fluent integration.
- `inquire` — terminal prompts with editor support.
- `otp-std` — HOTP / TOTP generation with `unsafe-length` to allow non-standard digit counts (the `otp add --digits` parser accepts 6–8; 6 is the RFC default).
- `qr2term` + `image` + `rqrr` — QR display and QR-from-image OTP import.
- `psl` — compile-time-embedded public suffix list. Used exclusively by `browser::matcher` to compute the registrable domain so URL matching is cross-eTLD-safe.
- `landlock` + `libc` (Linux only, see `[target.'cfg(target_os = "linux")'.dependencies]`) — sandboxing for the `image`/`rqrr` QR-decode path. Used exclusively by `cli::sandbox`; do not pull either into non-Linux code.
- `confy` is **no longer** used; the migration path in `Configuration::migrate_legacy_config_path` exists to relocate configs written by the legacy `confy` layout.
